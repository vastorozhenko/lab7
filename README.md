# ЛР №7. Програмний брандмауер

User-space брандмауер у вигляді TCP/UDP-проксі: кожне TCP-з'єднання і кожна UDP-датаграма перевіряються за таблицею правил (IP/порт/протокол). Правила змінюються через Admin API без перезапуску, події записуються в JSON-журнал, конфліктні й дубльовані правила виявляються автоматично. Права root не потрібні; використовується лише стандартна бібліотека Python.

## Швидкий старт
```bash
python firewall.py --config config.json
# В іншому терміналі:
curl -s http://127.0.0.1:8081/rules                                   # список правил
curl -s http://127.0.0.1:8081/rules -X POST -H 'Content-Type: application/json' \
     -d '{"action":"deny","proto":"TCP","dst_port":80,"priority":10}'  # додати правило
curl -s -o /dev/null -w "HTTP %{http_code}\n" -H "Host: example.org" http://127.0.0.1:8080/   # TCP через проксі
python udp_client.py --port 5353                                      # UDP через проксі (DNS-запит)
python analyze_logs.py logs/events.jsonl                              # аналіз журналу
```

## Архітектура

```
 клієнт ──TCP:8080──> [ Proxy (tcp_proxy) ] ──> example.org:80
 клієнт ──UDP:5353──> [ Proxy (udp_proxy) ] ──> 8.8.8.8:53
                             │ decide()
                      [ RuleEngine (RuleSet) ] <── зміни ── [ AdminAPI :8081 ] <── curl
                             │                                      │ save()/load()
                      [ Logger (jlog) ] ──> logs/events.jsonl    config.json
```

- **Proxy**: на кожне з'єднання/датаграму викликає `RuleSet.decide()`; якщо `deny`, з'єднання закривається, датаграма відкидається.
- **RuleEngine**: таблиця правил, перевірка полів, виявлення конфліктів. Змінюється на місці під замком, тому проксі одразу бачать зміни.
- **AdminAPI**: HTTP на 127.0.0.1:8081; зміни зберігаються в `config.json`.
- **Logger**: JSONL-журнал усіх рішень і змін правил.

## Структура правила

| Поле | Тип | Значення | За замовчуванням |
|---|---|---|---|
| `id` | int | призначається автоматично | - |
| `action` | string | `allow` або `deny` | `deny` |
| `proto` | string | `TCP` або `UDP` | `TCP` |
| `src_ip_cidr` | string | IP або мережа CIDR джерела | `0.0.0.0/0` (будь-яке) |
| `dst_ip_cidr` | string | IP або мережа CIDR призначення | `0.0.0.0/0` |
| `src_port` | int | 0..65535, 0 = будь-який | 0 |
| `dst_port` | int | 0..65535, 0 = будь-який | 0 |
| `priority` | int | менше число = вищий пріоритет | 100 |
| `enabled` | bool | `true` або `false` | `true` |

**Порядок перевірки:** правила сортуються за `priority`, при рівному пріоритеті раніше додане (менший `id`) перевіряється першим; застосовується перше правило, що збіглося. Якщо жодне не збіглося, діє політика за замовчуванням `allow`.

Некоректні значення (невідома дія чи протокол, неправильний CIDR, порт поза діапазоном, `enabled` не логічного типу, невідомі поля) відхиляються з кодом 400 і поясненням.

## Admin API

| Метод і шлях | Дія |
|---|---|
| `GET /rules` | список правил у порядку перевірки |
| `POST /rules` | додати правило (201; 409 якщо дублікат/конфлікт) |
| `PATCH /rules/{id}` | змінити поля, наприклад `{"enabled": false}` |
| `DELETE /rules/{id}` | видалити правило (404 якщо немає) |
| `POST /reload` | перечитати `config.json` (наприклад, після ручного редагування) |
| `GET /conflicts` | перевірити всю таблицю на конфлікти |

Усі зміни діють одразу, без перезапуску, і зберігаються в `config.json`.

## Виявлення та вирішення конфліктів

Під час `POST` і `PATCH` нове правило порівнюється з наявними:

| Ситуація | Реакція | Чому |
|---|---|---|
| **Дублікат:** ті самі протокол, адреси, порти і дія (будь-який пріоритет) | правило відхиляється (409) | друге правило нічого не змінює |
| **Конфлікт:** ті самі протокол, адреси, порти і пріоритет, але різна дія | правило відхиляється (409) | результат залежав би лише від порядку додавання |
| **Перекриття:** є трафік, що підпадає під обидва правила, дії різні | правило додається з попередженням, у якому сказано, яке правило переможе | так задаються винятки, наприклад «заборонити всім, крім адміністратора» |
| **Затінення:** раніше перевірюване правило охоплює весь трафік нового | правило додається з попередженням «this rule will never apply» | правило марне, його варто видалити або підвищити пріоритет |

Перекриття й затінення аналізуються лише між увімкненими правилами. `GET /conflicts` і `POST /reload` виконують ту саму перевірку для всієї таблиці, тому конфлікти, внесені ручним редагуванням `config.json`, теж виявляються.

**Як вирішувати:** дублікат видалити; для конфлікту змінити пріоритет одного з правил; для перекриття переконатися, що перемагає потрібне правило (за потреби змінити пріоритет); затінене правило видалити або підняти йому пріоритет.

## Журнал

`logs/events.jsonl`, один JSON-запис на рядок, час у UTC:

| Подія | Поля |
|---|---|
| `tcp.connect`, `udp.packet` | `action`, `proto`, `src` [ip, port], `dst` [ip, port], `rule_id`, `reason` (опис правила або політика за замовчуванням), для UDP `bytes` |
| `rule.add`, `rule.update`, `rule.delete`, `rule.rejected`, `rules.reload` | зміни правил, попередження, помилки |
| `tcp.error`, `udp.error` | помилки з'єднання з призначенням |

**Пошук і аналіз** (`analyze_logs.py`):
```bash
python analyze_logs.py logs/events.jsonl                          # статистика, топ джерел, тривоги
python analyze_logs.py logs/events.jsonl --action deny             # усі блокування
python analyze_logs.py logs/events.jsonl --proto UDP --rule 4      # за протоколом і правилом
python analyze_logs.py logs/events.jsonl --src 127.0.0.0/8 --dst-port 80 --since 2026-11-11T18:00:00Z
python analyze_logs.py logs/events.jsonl --event rule              # зміни правил
```
Тривога ALERT формується, якщо з однієї IP-адреси заблоковано 5 і більше з'єднань чи пакетів (`--threshold`).

## Зміни відносно демо-пакета
1. `POST /reload` створював новий набір правил, а проксі продовжували використовувати старий: API показував одні правила, а фактично діяли інші. Тепер набір змінюється на місці.
2. Зміни через API не зберігалися і зникали після `reload`; тепер вони записуються в `config.json`.
3. Конфлікти виявлялися лише для повністю однакових правил з однаковим пріоритетом. Додано дублікати з іншим пріоритетом, перекриття і затінення, а також `GET /conflicts`.
4. Додано перевірку полів правила: раніше неправильний CIDR приймався, і правило мовчки ніколи не спрацьовувало, а `"enabled": "false"` вважалося увімкненим.
5. Некоректний JSON в API обривав з'єднання без відповіді; тепер повертається 400. `DELETE` неіснуючого правила повертає 404.
6. Доступ до таблиці правил з кількох потоків захищено замком.
7. У журнал додано причину рішення (`reason`), протокол, читабельний час і події змін правил.
8. `analyze_logs.py`: пошук за дією, протоколом, джерелом, портом, правилом і часом; групування джерел за IP без порту.
9. Адреса Admin API береться з `config.json` (раніше була жорстко задана в коді).
10. Додано `udp_client.py` для демонстрації UDP.

## Обмеження
- Це **user-space** проксі, а не системний фільтр пакетів: фільтрується лише трафік, що йде через порти проксі.
- Продуктивність нижча, ніж у фільтрів ядра (nftables/iptables, eBPF).
- Admin API без автентифікації, доступний лише з 127.0.0.1.
- Для промислового використання: nftables/iptables, Windows Filtering Platform, PF або eBPF/NFQUEUE з правами адміністратора.
